# 退避スペースへの移動を「列」ではなく「スペース全体」にする — 設計書

対象コミット: `9604f45`（行番号はすべてこの時点のもの）

## 1. 何を直すか

退避スペースが完全に空で、空き容量が残っているのに、**一度に 22 枚以上を落とすと何も起きない**。
メッセージも出ず、選択だけが残る。

| 落とす枚数 | 結果 |
|---|---|
| 20 | 入る |
| 21 | 入る |
| 22 | 入らない（無反応） |
| 25 | 入らない（無反応） |

原因は `applyMove()`（`files/index.html:3666`）が落とし先を1つの列に決め打ちすることにある。
`growStashCol()`（同 3798）はその列の高さを `STASH_COL_MAX_H`(21) までしか伸ばさないので、
空の列に 22 枚を落とすと高さ 21 で頭打ちになり、`validateMove()` が「移動先の空きが足りません」で
弾いて移動を丸ごと中止する。

利用者にこの制約が見えないのは、描画の前に `ensureStashRoom()` → `repackStash()` が走り、
退避スペースの全列を `h:STASH_COL_H`(4) で積み直すためである。21 段の列は画面に一度も表示されない。

## 2. 決定事項

| 論点 | 決定 |
|---|---|
| 落とし先 | 退避スペースが宛先のときは列を見ない。スペース全体へ自動で詰める |
| 実装の形 | 退避専用の経路を分ける。倉庫側の `validateMove` / `moveCells` / `movingCount` は触らない |
| 容量の上限 | **その日の入力総パレット数**（`Σ lot.pallets`）。定数をやめる |
| 入りきらないとき | 1マスも動かさない。理由を `alert()` で出す（部分移動はしない） |
| `STASH_COL_MAX_H`(21) | 削除する（`growStashCol` ごと消える） |
| `STASH_MAX_COLS`(14) | 削除する（上限をパレット数だけで見る） |
| 列の枠に落としたとき | 受け皿に落としたときと同じ。全体扱いにする |

## 3. 宛先の扱い

`applyMove(spaceName, colIndex)` の冒頭で宛先が退避ゾーンかを判定し、退避なら
`applyMoveToStash()` へ委譲する。`colIndex` は使わない。

```
applyMove(name, col)
  ├ 退避か？ ─ yes → applyMoveToStash()      新設。列を見ない
  └           no  → 従来どおり validateMove / moveCells（変更なし）
```

`applyMoveToStash()` の積み方は `putToStash()`（同 3775）と同じにする。
空いている列から詰め、足りなければ `h:STASH_COL_H` の列を足す。**列の高さは伸ばさない。**

### 3-1. 呼び出し元

| 場所 | 現在 | 変更後 |
|---|---|---|
| 受け皿に落とす（`files/index.html:3734`） | `applyMove(s.name, firstFreeStashCol())` | `applyMoveToStash()` を直に呼ぶ |
| 列の枠に落とす（同 3738） | `applyMove(w.dataset.space, parseInt(w.dataset.col))` | 変更なし（委譲で全体扱いになる） |
| 倉庫へ戻す（同 4304） | `applyMove(cand[0].name, cand[0].idx)` | 変更なし（宛先が倉庫なので素通り） |
| ドラッグ中の色付け（同 3629） | `validateMove(...)` を直接呼ぶ | 宛先が退避なら退避用の検証を呼ぶ |

`highlightDrop()` を直さないと、列の空きで緑／赤を出したまま実際の可否と食い違う
（「赤いのに落ちる」「緑なのに落ちない」）。

### 3-2. `applyMoveToStash()` が引き継ぐ責務

`applyMove()` は配置を変える唯一の経路なので、専用経路も同じ責務を満たす。

1. `isActiveFresh()` の確認（古ければ `refreshFreshness()` して中止）
2. `snapshotSpaces(lastSp)` と `selSnapshot()` を**書き換えの前に**控える
3. 検証（§5）
4. 成功時: `lastSp` を差し替え、`pushMoveStep(spBefore, selBefore)`、`saveManual()`、`clearSel()`、`redraw()`
5. 失敗時: 何も変えずに理由を出す

`growStashCol()` が無くなるので、「検証の前に `lastSp` が伸びる」という状態自体が消える。
`9604f45` で入れた復元関数（`ungrow`）の取り回しも不要になる。

### 3-3. 分割確認は出ない

退避への移動では `needConfirm` は成立しない。`blockCountOf()` が退避を数えないため、
移動後に倉庫側の箇所数が増えることがないからである（`after > before` にならない）。
確認ダイアログは出さない。

## 4. 容量の決め方

```js
// その日の入力にあるパレット数。盤に乗っている荷物は必ずこれ以下になる
function stashCapacity(lots){
  return (lots || lastLots || []).reduce((a, l) => a + (l.pallets || 0), 0);
}
function stashFreeRoom(sp){
  return Math.max(0, stashCapacity() - stashTotal(sp));
}
```

**なぜ入力総数か。** 盤に乗っている荷物と退避にある荷物の合計は、常にその日の入力総数以下である。
したがって「倉庫にあるものを全部退避へ逃がす」が、どの日でも必ず成立する。過不足のない唯一の値になる。

倉庫の総容量（実測 178P。`usableCount` の合計、うち通路列 11P・通路マス 9P）を上限にする案も
検討したが、**入力総数が倉庫容量を超える日に成立しない**。その日はあふれ分が既に退避へ入っており
（`files/index.html:2781`）、そこから倉庫側を全部どかすには「倉庫にある分＋既に退避にある分」＝
入力総数ぶんの容量が要るためである。

### 4-1. 副作用

- 自動配置のあふれ経路（同 2781）も同じ `stashFreeRoom()` を通る。上限が入力総数になるため、
  あふれた分は必ず退避へ入る。`l.noRoom`（退避にも入らなかった分）は通常運用では常に 0 になる。
  分岐そのものは残す（入力が無い状態など、想定外の入口に対する守りとして意味がある）
- 入力を編集して総数が減ると上限も下がる。既に退避にある分が上限を超える状態は起こりうるが、
  `Math.max(0, ...)` により「空きが 0」になるだけで破綻しない
- 入力が空（`lastLots` が空）のときは上限 0。そのとき盤にも荷物が無いので、実害はない

### 4-2. 列数の上限は持たない

上限はパレット数だけで見る。列数は `repackStash()` が中身から決める。
`ensureStashRoom()` の「末尾に空き列を1本残す」条件（同 3850）は
`s.cols.length < STASH_MAX_COLS` から「容量が残っていれば足す」に変える。

## 5. 検証

```js
validateStashMove(sp, lotId, counts) -> {ok, same?, reason?, next?}
```

1. 動くマス数 `n` = `counts` のうち**退避以外**のキーの合計。すでに退避にあるマスは動かない
2. `n <= 0` → `{same:true}`。従来どおり無反応（退避の中では位置に意味が無いため）
3. `n > stashFreeRoom(sp)` → `{ok:false, reason}`（§6）
4. `next` を作る — 複製 → 倉庫側から減算 → `putToStash()` で積む

倉庫と退避が混在した選択でも、1 の数え方により倉庫側のマスだけが動く。

### 5-1. `clone()` の `blockedRows` 落ち

`clone()` は JSON 経由なので `blockedRows`(Set) が消える。`validateMove()` は複製の直後に
Set を貼り直している（同 3218）。同じ処理が 2 か所に必要になるので、`cloneSpaces(sp)` として
切り出し、`validateMove()` と `validateStashMove()` の両方から呼ぶ。コピーを増やさない。

## 6. 入りきらないときの見せ方

1マスも動かさず、`alert()` で理由を出す。

```
退避スペースに入りきりません。
選んだのは 30P、いま空いているのは 12P です。
```

- `alert()` を選ぶのは、操作の直後に結果を返す必要があるためである。
  倉庫へ戻せないときの既存処理（同 4301）も `alert()` なので、失敗の伝え方が揃う
- 成功時は従来どおり無言
- 「動くマスが無い」場合（§5 の 2）は従来どおり無反応。ここでメッセージを出すと、
  退避の中でマスを動かすたびにダイアログが出て邪魔になる

## 7. 消すもの

| 対象 | 場所 | 理由 |
|---|---|---|
| `STASH_COL_MAX_H` | 3748 | 参照は `growStashCol` の 1 か所のみ |
| `growStashCol()` | 3798 | 新経路は列を足す。高さを伸ばさない |
| `firstFreeStashCol()` | 3789 | 受け皿経路が `applyMoveToStash()` 直呼びになり参照ゼロ |
| `STASH_MAX_COLS` | 3747 | 上限がパレット数基準になる。参照3か所を書き換え |

`stashFreeRoom()` のコメント（3766-3770）は「実効の上限は 14×4=56P」という誤った根拠を
記録しているので、§4 の根拠に差し替える。

## 8. 技術制約（実測）

すべて `9604f45` のコードに対し、ローカルサーバー（`python3 -m http.server 8765 --directory files`）で
2026-09-21 に実測した。ドラッグは合成イベントで再現できないため、**アプリ自身の
`putToStash()` / `renderResult()` を JavaScript から直接呼んで状態を作った**。

### 8-1. 列が増えても描画は壊れない

| 列数 | 退避量 | 受け皿の外形 | 受け皿の横スクロール幅 | ページの横あふれ |
|---|---|---|---|---|
| 14 | 56P | 240×210 のまま | 224 → 469 | なし |
| 17 | 68P | 240×210 のまま | 224 → 568 | なし |
| 30 | 120P | 変わらず | 108 → 937 | なし |
| 60 | 240P | 変わらず | 108 → 1867 | なし |
| 120 | 480P | 変わらず | 108 → 3743 | なし |

PC 幅（1024）とスマホ幅（375）の両方で同じ。受け皿は `.sb-body{overflow:auto}`（同 373）で
横スクロールするだけで、外形は変わらない。`document.scrollWidth === clientWidth` のままで、
ページ全体の横あふれは発生しない。再描画 4 回の合計は 47ms。

**したがって、既存の 2026-09-17 設計書 §3-3 にある「65P を入れると 17 列になり、
`STASH_MAX_COLS` を超えて隅の小さな盤の描画が崩れる」は事実ではない。**
`.sb-body` のスクロールを見落とした記述であり、56P という上限に技術的な裏付けは無かった。

### 8-2. 一度に見える列数は増えない

受け皿に一度に見えるのは PC で約 7 列（28P）、スマホで約 3.5 列（14P）。それ以上は横スクロールになる。
上限を上げても「一目で読める量」は変わらない。2026-09-03 設計書 §5-1 の
「1マス18pxで4段×5列＝20パレットが一目で入る」という意図は、上限とは独立に保たれる。

`STASH_COL_H`(4) は隅の受け皿に収まる段数として決まった値なので、変更しない。

### 8-3. 紙の制約は件数で来る（今回の変更とは独立）

退避の中身は `stashSlots()` で「※未定」として紙に載る。まとめ欄は実測で 5 件までが 1 ページに収まり、
6 件で用紙の約 104% に達して警告が出る（`files/index.html:5282` のコメント、`PRINT_H_LIMIT`）。

この制約は**件数**で決まり、パレット数の上限とは連動しない。現在の 56P でも 1P × 56 ロットを
入れられるため、上限の引き上げが件数を増やすわけではない。
今回は紙側に手を入れない。`~/claude-lessons/lessons.md` の
「[2026-09-18] 印刷1ページの『高さ予算』を見積もらずに縦積みの欄を設計した」に照らし、
高さ予算に影響する変更を含まないことをここに記録しておく。

### 8-4. 非表示タブでは寸法が測れない

配置編集タブが表示されていないあいだ、`#stashDock` の `getBoundingClientRect()` は 0 を返す
（`[2026-08-23] 非表示タブでは getBoundingClientRect() が 0 を返し…` と同じ）。
ブラウザで確認するときは `switchTab("edit")` を先に呼ぶ。

### 8-5. PWA キャッシュ

`files/index.html` を変更するので `files/sw.js` の `CACHE_VERSION` を **v68 → v69** に上げる。
上げないとインストール済みの端末に更新が届かない。

## 11. やらないこと

- 退避スペースを「高さ可変の1列」に作り替える（マスのキー `エリア名|列|行` が変わり、

## 12. 動作確認の手順

ローカルサーバーを起動する。

```bash
python3 -m http.server 8765 --directory files
```

ブラウザで `http://localhost:8765/` を開く。設定タブで「入力タブに『基本サンプル』『混載デモ』を出す」を
入れ、入力タブで「基本サンプル」→「▶ 自動配置を作成」。

確認する内容。

1. 部品C / L-103（25P）を全部選び、退避の受け皿へドラッグする → 25 枚とも入る（現在は無反応）
2. 同じ操作を退避スペースの列の枠に落として行う → 受け皿と同じ結果になる
3. 戻す（↩）を押す → 移動前の形に戻る
4. 入力総数を超える量を落とす → 何も動かず、`alert` に空き容量が出る
5. 退避スペースの表示が崩れない（PC 幅・スマホ幅の両方）

退避スペースの中身は自動配置し直しても残るので、条件を作り直すときは `localStorage` の
`palletApp.*` を消して読み込み直す。

実機（Pixel 9a / Android Chrome）で確認するときは、同じ LAN から
`http://<PC の IP>:8765/` を開く。

終了はサーバーを起動したターミナルで `Ctrl+C`。
