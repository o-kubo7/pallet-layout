# スペースの掲載先属性と設定の永続化 — 設計書

- 作成: 2026-08-29　最終更新: 2026-08-30
- 状態: 承認済み
- 元になったメモ: `docs/memos/2026-08-27-sheet-improvements-memo.md` の「1-1」「1-2」
- 対象ファイル: `files/index.html`、`files/sw.js`

---

## 1. 目的

配置図の表（以下「配置表」）に、スペース設定で追加したエリアが出ないという穴を塞ぐ。
あわせて、スペース設定を localStorage に保存して恒久設定にする。

メモの実装順序では、この 2 つが最初に来る。現場で使える場所をすべて洗い出して
配置マス設定を更新する方針を取る以上、洗い出しの結果を入れる器を先に作る必要があるため。

### 1-1 いま何が起きているか

配置表の上段・下段に出すエリアが、エリア名のハードコード配列になっている。

```js
const SHEET_TOP = ["軒下①","軒下②"];
const SHEET_BOTTOM = ["メイン","PC横","EV横"];
```

設定でエリアを追加しても、どちらの配列にも名前が無いので、そのエリアに置かれたロットは
配置表から消える。警告は出るが、表に出す手段が無い。

### 1-2 いま何が起きていないか

スペース設定は `applyConfig()` が実行時の `SPACES` を書き換えるだけで、保存されない。
リロードすると `DEFAULT_SPACES` に戻る。設定カードのバッジにも
「微調整用・保存されません」と書いてある。

---

## 2. 用語

このプロジェクトでは「段」が 2 つの意味を持つため、以下のように呼び分ける。

| 呼称 | 意味 | 該当する設定・コード |
|---|---|---|
| 段 | 倉庫の 1 列に何パレット積めるか | 設定の 5 項目目「各列の高さ」、`cols[].h`、配置表の「段番号」列 |
| 掲載先 | 配置表のどのブロックに欄を書くか | 今回追加する属性。上段 / 下段 / あふれブロック |

以降、「段」は倉庫の段数の意味だけで使う。

## 3. 決定事項

1. 掲載先の値は「上段 / 下段 / あふれブロック」の 3 つとする。「表示しない」は作らない。
2. あふれブロックの描画は今回の範囲に含めない。メモ §5（テーブル分割）とセットで後から実装する。
   今回はあふれブロックを指定したエリアを警告に出すだけにする。
3. 設定の入力欄は現在の textarea のままとし、行の 6 項目目として掲載先を追加する。
   表形式 UI への作り替えはメモ 2-7（設定タブのサブタブ化）で行う。
4. 掲載先は `SPACES` の各要素のプロパティとして持たせ、`SPACES` の配列全体を保存する（A 案）。
5. 掲載先を変更しても、ブロック図で手動調整した配置は破棄しない。
   破棄するのは倉庫の形（列構成）が変わったときだけとする。
   これには `applyConfig()` の分岐と指紋からの除外の両方が必要になる（§8）。
6. 下段の先頭エリアを特別扱いする。自動注釈を付けない基準エリアであり、
   かつ流し込みで上段へ溢れない固定エリアでもある。

### 3-1 A 案を採った理由と、承知しているデメリット

掲載先だけを別のオブジェクト（エリア名 → 掲載先のマップ）で別キーに保存する案（B 案）も
検討した。B 案は幾何と表示の関心が分離するが、設定の textarea の 1 行に掲載先が出るのに
データは別キーにある、という食い違いを設計に残す。エリア名を変更したときにマップが孤児に
なるため、同期処理も必要になる。6 項目目に掲載先を入れる決定と構造が一致する A 案を採る。

A 案のデメリットは以下の 5 点。1・2・5 は対策を設計に織り込む。3 と 4 は受け入れる。

1. **壊れた保存の被害範囲が広い。** `SPACES` は配置アルゴリズム・ブロック図の描画・配置表・
   収容能力表示・指紋の土台。`loadData()` は `JSON.parse` の失敗しか握らないので、
   JSON として valid で構造が壊れている保存は素通りする。単一 script のため、
   `drawZone()` あたりで例外が飛ぶとそこから下（Service Worker の登録を含む）が
   丸ごと実行されなくなる。→ §7-3 の構造検証で塞ぐ。
2. **指紋の除外が文字列化のレベルでしか切れない。** 掲載先と列構成が同じ配列に同居するため、
   `spacesToText()` に引数を足して出し分けることになる。→ §8-2 で対処。
3. **保存の粒度が粗い。** 掲載先を 1 つ変えただけでも `SPACES` 全体を書き戻す。
   別タブで開いていると last-write-wins で列構成ごと巻き戻る。単一タブ運用のため実害は小さい。
4. **メモ 2-7 のサブタブ化で境界がにじむ。** 掲載先は表示側の関心だが、データは配置マス側に
   埋まる。サブタブ化のときに再検討する。
5. **一度保存すると `DEFAULT_SPACES` の更新が届かない。** これから場所の洗い出しをして
   `DEFAULT_SPACES` を書き換える作業が控えているため、開発中に古い保存が居座り、
   コードを直したのに画面が変わらないという事故が起きやすい。→ §7-1 の保存バージョンで塞ぐ。

## 4. データ構造

`SPACES` の各要素に `sheet` を追加する。

```js
{name, zone, orient, block, align, cols, sheet}
```

`sheet` の値は `"top"` / `"bottom"` / `"over"` の 3 つ。

`DEFAULT_SPACES` の既定値は、現行の `SHEET_TOP` / `SHEET_BOTTOM` と同じ割り当てにする。

| エリア | sheet |
|---|---|
| メイン | `"bottom"` |
| 軒下① | `"top"` |
| 軒下② | `"top"` |
| PC横 | `"bottom"` |
| EV横 | `"bottom"` |

既定値に `"over"` は含めない。

`SHEET_TOP` / `SHEET_BOTTOM` の const は削除し、`SPACES` から導出する関数に置き換える。

```js
function sheetAreas(tier){ return SPACES.filter(s=>(s.sheet||"bottom")===tier).map(s=>s.name); }
```

`SHEET_TOP_SLOTS`（4）と `SHEET_BOTTOM_SLOTS`（7）は据え置く。欄数は紙のレイアウトから
決まる値であり、エリアの数とは別の話であるため（メモ §3）。

## 5. 下段の先頭エリア

下段のうち、設定の並び順で最初に来るエリアを特別扱いする。現行の並びではメインが先頭に
来るため、既存の動作と変わらない。

このエリアは次の 2 つを兼ねる。

- **自動注釈を付けない基準エリア**（今回実装する）
- **流し込みで上段へ溢れない固定エリア**（今回は実装しない。§11 に記録）

`renderSheet()` にあるエリア名の直書きを、導出に置き換える。

```js
// 変更前
const bottom = sheetEntries(SHEET_BOTTOM, "メイン");
// 変更後
const bottomAreas = sheetAreas("bottom");
const bottom = sheetEntries(bottomAreas, bottomAreas[0] || null);
```

自動注釈のルール自体は現行のまま。基準エリア以外に置かれたロットに `※PC横` のような
注釈が付く。上段の注釈行は今回作らない。

## 6. 設定の入力形式

行形式を 6 項目に拡張する。

```
名前 | near/far | v/h | ブロック列数 | 各列の高さ | 掲載先
```

- 掲載先の値は `top` / `bottom` / `over`
- **6 項目目は省略できる。** 省略した場合は、同名のエリアが現在の `SPACES` にあれば
  その掲載先を引き継ぎ、無ければ `bottom` とする。
  `applyConfig()` は既に `prev.align` で同じことをしているので、そのパターンを踏襲する
- 不正な値は既存と同じく `alert` で拒否し、`SPACES` を書き換えない
- 5 項目必須のチェック（`p.length<5`）はそのまま残す。6 項目目が任意であるため
- 設定カードの hint に掲載先の説明を追記する

`spacesToText()` は 6 項目目を出力するようにする（§8-2 の引数を参照）。

**§7-3 との非対称について**: ユーザーが打った文字列は `alert` で拒否し、保存から読んだ値は
矯正して読む。意図した非対称である。前者は打ち直せるので、黙って別の値に変えると
打った内容と保存された内容が食い違う。後者は打ち直す手段が無いので、
拒否すると設定全体を失う。

## 7. 保存と復元

### 7-1 保存

`STORE_KEY` に `spaces` を追加する。

```js
const STORE_KEY = { ..., spaces:"palletApp.spaces" };
const SPACES_SAVE_VERSION = 1;
```

保存する値はバージョン付きにする。

```js
saveData(STORE_KEY.spaces, {v:SPACES_SAVE_VERSION, spaces:SPACES});
```

- **保存するタイミング**: `applyConfig()` が検証を通り `SPACES` を書き換えた直後
- **破棄するタイミング**: `resetConfig()`。「初期値に戻す」は保存も消す
- 設定カードのバッジを「微調整用・保存されません」から「この端末に保存」に変更する

`DEFAULT_SPACES` をコード側で更新したときは `SPACES_SAVE_VERSION` を上げる。
古い保存はバージョン不一致で読まずに捨てられ、更新した既定値が届く。

### 7-2 復元

`initSpaces()` を IIFE として init の先頭（`cfgText` を埋める行の前）に置く。
既存の `initMaster()` / `initLots()` / `initFrac()` と同じパターンにする。

処理の順序は次のとおり。

1. `loadData(STORE_KEY.spaces)` を読む。`null` なら何もしない（`DEFAULT_SPACES` のまま）
2. `d.v !== SPACES_SAVE_VERSION` なら保存を消し、`DEFAULT_SPACES` のままにする
3. `validSpaces(d.spaces)` が偽なら保存を消し、`DEFAULT_SPACES` のままにする
4. 検証を通ったら矯正をかけたうえで `SPACES` に入れる

### 7-3 構造検証と矯正

必須は「名前」と「列」だけとし、それ以外は矯正して読む。

**破棄する条件**（1 つでも該当したら保存全体を捨てる）

- 配列でない、または空
- 要素がオブジェクトでない
- `name` が文字列でない、または空文字
- `cols` が配列でない、または空
- `cols[].h` が正の有限数でない

**矯正する条件**（値を差し替えて読み進める）

- `zone` が `near` / `far` 以外 → `DEFAULT_SPACES` の同名から引く。無ければ `near`
- `orient` が `h` 以外 → `v`
- `block` が数値でない → `99`
- `sheet` が `top` / `bottom` / `over` 以外 → `bottom`
- `cols[].aisle` は真偽値に正規化する

### 7-4 読み込めなかったことを知らせる

バージョン不一致または構造不正で保存を捨てた場合、`DEFAULT_SPACES` を使ったうえで
設定カードに知らせる。`<div id="cfgNote">` を新設し、次の文言を出す。

> 保存されていた設定を読み込めなかったので、初期値に戻しました。

黙って戻すと、設定が消えた理由がユーザーに分からない。バージョン不一致は開発側の都合だが、
ユーザーから見れば「設定が消えた」という同じ事象なので、文言は共通で構わない。

## 8. 手動調整を残す仕組み

掲載先を変更しても、ブロック図で手動調整した配置を残す。これには 2 つの変更が必要で、
どちらか片方だけでは成立しない。

### 8-1 `applyConfig()` の分岐（再配置を走らせない）

`run()` は 「配置し直したので手動調整は捨てる」というコメントとともに `clearManual()` を
呼んでいる。`applyConfig()` は末尾で必ず `run(false)` を呼ぶため、**現状では掲載先しか
変えていなくても、「設定を反映」を押した時点で手動調整が消える。**

`applyConfig()` に分岐を足す。反映の前後で `spacesToText(false)`（掲載先を除いた幾何）を
比較する。

- **幾何が同一** … 掲載先しか変わっていない。`redraw()` を呼ぶ。
  `run()` を通らないので `clearManual()` が走らず、手動調整が残る
- **幾何が変化** … 現行どおり `run(false)` を呼ぶ。手動調整は捨てる

`redraw()` は再配置せずに `renderResult()` を呼ぶだけなので、この用途にそのまま使える。

幾何が同じであれば `lastFp` と保存済みの `manual` はどちらも書き換える必要がない。
`lastSp` は配置結果の複製であり、`SPACES` のオブジェクトが差し替わっても影響を受けない。

### 8-2 指紋から掲載先を外す

`spacesToText()` に引数を足す。

```js
function spacesToText(withSheet=true){ ... }
```

`inputFingerprint()` は `spacesToText(false)` を使う。

掲載先は紙のどこに書くかであって倉庫の形ではないため、変更しても手動調整した配置を
破棄しない。破棄するのは列構成・区分・名前が変わったときだけとする。

これが効くのはリロードのときである。`restoreManual()` は保存された指紋を現在の `SPACES` から
作った指紋と比べ、一致しなければ捨てる。`SPACES` が保存されるようになるため、掲載先を
指紋に含めたままだと、掲載先を変えた後のリロードで手動調整が捨てられる。

**8-1 とセットで初めて意味を持つ。** 8-1 が無ければ「設定を反映」の時点で手動調整が
消えているので、リロード時に復元するものが残っていない。

**副次的な利点**: `withSheet=false` の出力は 5 項目で現行と完全に同じ文字列になる。
そのため、既存の保存済み手動調整がこの改修を跨いで生き残る。

**あわせて直すもの**: `inputFingerprint()` の直前にあるコメントは、列構成を指紋に含める理由を
「`SPACES` が localStorage に保存されておらず、リロードで `DEFAULT_SPACES` に戻るため」と
説明している。今回この前提が成立しなくなるので、コメントを書き換える。
保存されるようになっても、列構成が変われば保存済みの配置が乗らないという理由は残る。

## 9. 警告

現行の `noSlotAreas` は「`SHEET_TOP` にも `SHEET_BOTTOM` にも属さないエリア」を拾っている。
今回の矯正により掲載先は必ず 3 値のいずれかになるので、この状態は発生しなくなる。

代わりに、あふれブロックを指定したエリアを拾う。

`overTop` / `overBottom`（欄数の超過）は現行のまま。参照する名前の配列を
`sheetAreas("top")` / `sheetAreas("bottom")` に置き換えるだけとする。

## 10. 技術制約

### 10-1 localStorage

このアプリは既に品目マスタ・荷物の入力・手動調整・表示設定を localStorage に保存している。
今回はキーを 1 本増やすだけで、新しい API 依存は発生しない。

- **容量**: オリジンあたり 5MB 程度。`SPACES` は数 KB なので問題にならない
- **使えない環境**: 既存コードが起動時に書き込みテストを行い、失敗したら `storageOK=false` として
  メモリ保持へフォールバックする。設定タブに「この環境では保存されません」と表示される。
  この仕組みにそのまま乗る
- **永続性**: iOS Safari は ITP により、一定期間アクセスの無いサイトのスクリプト書き込み
  ストレージを削除する。ホーム画面に追加した PWA はこの対象外。いずれにせよ、
  より重要な品目マスタと荷物の入力が既に同じ条件で保存されているため、
  今回の変更でリスクの水準は変わらない

### 10-2 Service Worker

`files/sw.js` は cache-first で `index.html` を配信する。`CACHE_VERSION` を上げないと、
インストール済みの PWA に更新が届かない。**v18 から v19 に上げる。**

これは 2026-07-09 の教訓（`~/claude-lessons/lessons.md`）に記録がある。
`index.html` を変更する作業は「軽微」ではない。

### 10-3 検証手段

ビルドツールもテストランナーも無い単一 HTML の PWA のため、検証はブラウザでの手動確認になる。
`~/.claude` のメモリに記録された「ブラウザ検証の罠」に従い、次を守る。

- 合成イベントは `isTrusted:false` で既定動作を持たない。`applyConfig()` / `resetConfig()` は
  ハンドラを直接呼んで検証する
- textarea への入力は `.value=` の直代入で行う。今回は `change` に依存する処理が無いため、
  これで問題ない
- ローカル検証時は Service Worker の登録解除と Cache Storage のクリアを行う。
  行わないと旧キャッシュを見続ける

## 11. 今回の範囲外（記録のみ）

### 11-1 欄の流し込み

配置表の欄が上段・下段の欄数に収まらなかったときの行き先。今回は実装しない。

```
下段の先頭エリア（メイン）    … 下段に固定。上段へは溢れない
下段のそれ以外（PC横・EV横）  … 下段 → 空きが無ければ上段
上段のエリア（軒下①②）      … 上段
上下段に収まらない分          … あふれブロック
```

上段が溢れた場合の行き先もあふれブロックとする。

この規則から、上段にも PC横・EV横 の注釈行が必要になる。現在、注釈行があるのは下段だけ。
上段に行を足すと表の高さが増えるため、メモ §3-2 の高さ予算に影響する。

### 11-2 あふれブロックの描画

メモ §3-3 の構成（メインの右に 84px 幅で縦積み、2 欄）。
テーブル分割・メイン 588px への圧縮・引き出し線の座標原点の変更・印刷倍率の自動計算と
セットで実装する。

### 11-3 触らないもの

- `SHEET_TOP_SLOTS`（4）/ `SHEET_BOTTOM_SLOTS`（7）。欄数は紙のレイアウト由来
- `FLOOR_POS`。未登録のエリアは自動配置にフォールバックするため、エリアを足しても
  ブロック図は壊れない
- `AREA_GROUPS`。`["軒下①","軒下②"]` のハードコードのままとする。
  **既知の穴**: 設定でエリア名を変更すると、この連結が外れて別エリア扱いになる。
  掲載先が設定可能になっても、この穴は残る

## 13. 完了の判定

以下がすべてブラウザ上で確認できたら完了とする。

1. 設定に新しいエリアを 1 行足し、掲載先を `bottom` にすると、そのエリアに置かれたロットが
   配置表の下段に出る
2. 同じエリアの掲載先を `top` に変えると、上段に出る
3. 掲載先を `over` にすると、配置表には出ず、あふれブロックが未実装である旨の警告が出る
4. 「設定を反映」の後にリロードしても、設定が保持されている
5. 「初期値に戻す」の後にリロードすると、`DEFAULT_SPACES` に戻っている
6. ブロック図で手動調整した後、掲載先だけを変更して「設定を反映」を押しても、
   手動調整した配置が残っている。さらにリロードしても残っている
7. 列の高さを変更して「設定を反映」を押すと、手動調整した配置が破棄される（現行どおり）
8. localStorage に壊れた値（`{"v":1,"spaces":[{"name":"x"}]}` など）を直接入れてリロードすると、
   初期値に戻り、設定カードに知らせが出て、ブロック図と配置表が正常に描画される
9. 6 項目目を省略した行を「設定を反映」しても、その行の掲載先が変わらない
