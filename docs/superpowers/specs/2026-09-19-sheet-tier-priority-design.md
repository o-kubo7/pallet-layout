# 配置図の欄割り当てを「掲載先＝優先する段」に変える 設計書

**状態**: 設計の合意済み（2026-09-19）。`/dig` の指摘を反映済み（2026-09-19）。実行計画はこれから作る。
**次の手順**: `superpowers:writing-plans` で実行計画を作る。

---

## 1. 背景

配置図の下段の欄が足りない日に、**メインエリアのロットが追記欄へ落ち、PC横・EV横 のロットが下段の欄を占める**。

### この現象をどこで見たか（2026-09-19 訂正）

初版はこの節を「現場から上がった実例（2026-09-18）」と書いていたが、**それは誤りだった**。
このアプリは現場でまだ一度も使われていない（2026-09-19 にユーザーが明言）。
下に挙げた例の品名（部品A〜E・製品W/X/Y/Z）は `DEFAULT_MASTER`（`files/index.html:946`）の
既定マスタそのもので、開発機でダミーデータを入れて描いた画面である。

- 下段8欄: 部品E, 部品C, **製品W(※EV横)**, 製品Y, 部品A, 製品Z, 部品B, **製品X(※EV横)**
- 追記欄のまとめ欄: 部品D・部品3 / L-104・333 / 14P・24P / 注記 **※メイン**・※PC横・EV横

**この設計は実運用データでは一度も検証されていない。** 動機となる現象の再現は、
すべて開発機のダミーデータによる（検証結果は §2）。現場で実際にどれだけの頻度で
起きるかは分かっていない。ただし「下段はまずメインで埋める」という運用ルール自体は
確定しているので、頻度と関係なく直す、という立場で着手する（2026-09-19 にユーザー確認）。

### なぜメインを優先するのか（本当の理由）

初版は「倉庫の主役だから」としか書いていなかったが、実際には紙の情報量の問題である。

- 盤（グリッド）のマスには**ロット名もロット番号も描かれない**。枠線と「半」だけ（`gridRows()`、`files/index.html:5084`）
- どのロットが盤のどこにあるかは、**下段の欄から引く引き出し線でしか分からない**（`drawLeaders()`、同 `4787`）
- 盤に描かれるのは `sheetAreas("bottom")[0]`（＝メイン）だけ。**PC横・EV横 は紙のどこにも図として描かれない**（同 `4995`）

つまり PC横・EV横 が下段の欄を取っても、引き出し線という下段欄の最大の価値をまったく使わない。
逆にメインが下段の欄を失うと、そのロットは盤の上で**位置を特定できない匿名の枠**になる。
見た目や序列の問題ではなく、紙から位置情報が消えるかどうかの問題。

### 原因

`files/index.html` の `arrangeBottomSlots()`。

```js
const keptRight=rightEntries.slice(0, Math.min(rightEntries.length, count));
const mainCap=Math.max(0, count-keptRight.length);
const keptMain=mainEntries.slice(0, mainCap);
```

`rightEntries`（基準エリア＝メイン以外、つまり PC横・EV横）が最大 `count` 件まで**先に**欄を取り、メインは残りだけを受け取る。あふれたメインは `dropped` から追記欄へ回る。

これは事故ではなく、`docs/superpowers/specs/2026-09-12-sheet-slot-proximity-design.md` の決定1「PC横・EV横の右詰めを**最優先**する」を実装したもの。**今回その決定を上書きする。**

### ユーザーの運用（2026-09-18 の指示、原文）

> 下段は、まずメインエリアのロットで埋める。メインエリアと軒下ではない置き場のロットは、上下段の空いた欄に注釈とともに記載する、欄が足りなければ追記欄に記載する。

## 2. 前提の変化（着手前に必ず確認すること）

**2026-09-19 に配置図の欄数を増やした**（コミット `feat: 配置図の欄を増やし、追記欄を2列にする`）。

- wide 様式が 16列×42px＝672px → **18列×39px＝702px**
- 上段 5→**6欄**、下段 8→**9欄**
- 追記欄が 156px の縦2枠 → **78px×2列×2段＝4枠**
- まとめ欄になるのは5件以上あふれた日だけ

**欄が3つ増えたぶん、メインがあふれる頻度自体が下がっている。**

### 確認結果（2026-09-19 実測、ダミーデータ）

着手ゲートとして「まだメインが追記欄に落ちるか」を確認した。**落ちる。現象は再現する。**

実運用データは存在しないため（§1）、`§6-1` の投入スクリプトが作るダミー（17行・216P）を
`palletApp.schedule` に流し込み、欄数拡張後のコードで `sheetPlacement()` を実行した。

- 様式: wide（上段6欄・下段9欄）
- 下段候補は11欄。内訳は**メイン系7欄・PC横3欄・EV横1欄**
- 現行コードは PC横・EV横 を先に4欄取るため、メインの枠が5に減る
- 結果: **メイン2件（品目4・品目5）が下段から落ち、追記欄へ**
- 追記欄は4件（メイン2＋退避2）。4枠に収まるので、まとめ欄にはならなかった

この構成でメイン優先にした場合を同じデータで試算すると:

- メイン優先・下段9欄: **メイン7件すべて下段に入る**。こぼれは PC横1・EV横1
- メイン優先・下段10欄（列を増やした場合）: メイン7＋PC横3。こぼれは EV横1

つまり**列を増やさなくても、優先順を変えるだけでメインのこぼれは解消する**（このデータでは）。

### 検証の限界

ダミーの数量分布は `[60,110,160,210]` の均等4種。メインが何欄になるかはロットの大きさ分布で
決まるので、実運用の分布が違えば発生頻度は変わる。また自動配置はメイン→軒下→PC横・EV横 の
順に埋める（`files/index.html:851`）ため、PC横・EV横 に荷物がある日は原則としてメインも
大量にある日である。**メインが下段の欄数（9欄）を超える日は、この変更を入れても追記欄へ落ちる。**
効くのは「メインが下段の欄数以下で、かつ PC横・EV横 に押し出されている」帯だけ。

## 3. 決定事項

### 3-1. 掲載先の意味を変える

エリアの掲載先（`sheet`: `top` / `bottom` / `over`）を「**固定の段**」から「**まず使う段**」に読み替える。
保存形式（`SPACES_SAVE_VERSION`）と設定画面の項目は変えない。値も `top`/`bottom`/`over` のまま。

現在のエリアと掲載先:

| 掲載先 | エリア |
|---|---|
| `top` | 軒下①、軒下②、出庫口横、5棟壁際 |
| `bottom` | メイン、PC横、EV横 |
| `none` | 退避 |

### 3-2. 各段の埋め方

その段を優先に設定されたエリアを、**設定タブの並び順**に詰める。

- 下段: メイン → PC横 → EV横
- 上段: 軒下① → 軒下② → 出庫口横 → 5棟壁際

**下段の右詰めは維持する。** メインを先に配り、残った欄に PC横・EV横 を**右端から**詰める。
盤のマス位置への近接配置の総当たり探索（`choose()`）は「メイン用に確保した欄の中」という定義のまま効く。
探索の組合せ数は最大 C(9,4)=126 程度で問題にならない。

**「EV横 を最右」は、PC横 と EV横 の両方が下段に残る日に限る**（2026-09-19 にユーザー確認）。
メイン優先にすると、右詰めに使える欄が1つしか残らない日が出る。そのときは**PC横 を残す**。
下段に入れられるなら PC横 から入れ、EV横 も一緒に入る場合に EV横 を右にする、という順番。
現行コードの `rightEntries.slice(0, count)` は並び順の先頭（＝PC横）から残すので、
**この点に実装変更は要らない**。「EV横 が必ず最右」という不変条件は成り立たない日がある、
と読み替えるだけでよい。

上段に右詰めの概念は無い（現状どおり並び順に詰める）。

### 3-3. 段をまたぐ回送（双方向・新規）

詰めきれなかった項目は、もう片方の段の空き欄へ注釈つきで回す。順番は決め打ちにする。

1. 各段、自段優先のエリアを配る（上段は「掲載先 top のエリア → 退避」の順に連結。現状のまま）
2. 上段のこぼれ → 下段の空き欄（**既存の `moved` / `fromTop`。現状のまま**）
3. 下段のこぼれのうち**メイン以外**（PC横・EV横） → 上段の空き欄（**新規**）
4. 残り全部 → 追記欄（順序は「実在する置き場 → 退避」＝現状のまま）

**2 と 3 は排他になる。** 下段があふれる日は下段の空きが 0 なので 2 は起きず、上段があふれる日は
上段の空きが 0 なので 3 は起きない。片方向ずつしか動かないので、順序で結果が変わることはない。

### メインは上段へ回さない（2026-09-19 に決定。初版の決定を撤回）

初版は「メイン自身が下段の欄数を超えた日も、メインを上段の空き欄へ回してよい」としていた
（2026-09-18 のユーザー確認）。**これを撤回する**（2026-09-19 にユーザー確認）。理由:

- 引き出し線は下段の欄からしか引かれない（`files/index.html:4787`）。メインを上段へ回すと線が切れ、
  **位置が分からなくなるのは追記欄に落とした場合と同じ**。得られるのは文字の大きさだけ
- 上段の見出しは「軒下」でハードコードされている（同 `4735`）。倉庫内の主力の荷物が
  「軒下」の見出しの下に、位置不明のまま並ぶ

したがって**メインのこぼれは追記欄へ直行**する。上段へ回すのは PC横・EV横 のこぼれだけ。
PC横・EV横 はもともと盤に描かれず引き出し線を持たないので、どちらの段にあっても情報は減らない。

なお「軒下」の見出しの下に他の置き場が並ぶこと自体は、すでに起きている（`※出庫口横`、
`※5棟壁際`、`※未定` が注釈で区別される）。PC横・EV横 を回しても新しい誤読は生まない。

### 退避の順位（2026-09-19 に確定）

**退避が先。現行の構造を変えない。** 退避は `sheetPlacement()` の先頭で上段の配列へ連結される
（`const top=sheetSlots("top").concat(stashSlots())`、`files/index.html:4596`）。この形のままなら、
上段の欄は「掲載先 top のエリア → 退避」の順で埋まり、**下段のこぼれ（手順3）が来る前に
退避が上段の欄を取る**。初版は手順3（下段のこぼれ）を手順4（退避）より先に書いていたが、
その順序を実装するには退避を `top` から外す構造変更が必要で、
`docs/superpowers/specs/2026-09-17-stash-overflow-sheet-design.md` の決定と、
`sheetLayout()` の wide 判定（退避も件数に数える）を両方壊す。**順序のほうを実態に合わせる。**

回された欄は注釈を作り直す（基準エリアを省かない）。既存の `fromTop` と同じ扱い。
引き出し線は盤のマスから引くので、盤に描かれない PC横・EV横 が回っても線は発生しない。

### 3-4. 様式の判定

**回送前の件数で行う**（現状の方針を維持）。先に wide にして欄を増やし、それでもあふれる分だけを回す。

## 4. 実装の構造

責任分担は維持する。`sheetPlacement()` が「どの項目をどちらの段に回すか」、
`arrangeBottomSlots()` が「下段の行のどこに置くか（右端固定＋近接配置）と何がこぼれるか」。

### 4-1. `arrangeBottomSlots()` — 優先順を入れ替える

下段に入る順位を次にする。

`基準エリア → 基準エリア以外（右詰め）→ 上段からの救済（退避を含む）`

救済を「基準エリア以外」より後ろにするのは、ユーザーの運用の「**空いた**欄に記載する」に
合わせたもの。自段のエリアが先。

**エリア名をコードに書かない。** 実装は一貫して `sheetAreas("bottom")` の並び順から引く
（`files/index.html:4478` のコメントが明示している既存方針）。基準エリアは
`sheetAreas("bottom")[0]`。設定タブでエリア名を変えても壊れないようにする。
この設計書で「メイン」「PC横」「EV横」と書いている箇所は、いずれも既定設定での具体名にすぎない。

### 4-2. `sheetPlacement()` — 回送を双方向にする

現在は上段→下段の一方向だけで、退避は無条件に上段の末尾へ連結している。

```
top = sheetSlots("top") + stashSlots()       // 退避の連結は現状のまま（§3-3）
lay = sheetLayout(top, 下段自前)             // 様式は回送前の件数で
下段の空き = lay.bottom - 下段自前の件数
moved     = top からあふれた分を下段の空きまで       // 既存。手順2
arranged  = arrangeBottomSlots(下段自前 + moved, lay.bottom, positions)
上段の空き = lay.top - top.length                    // 退避を数えた後の空き
回送      = arranged.dropped のうち基準エリア以外を、上段の空きまで   // 新規。手順3
追記欄    = 残り（実在する置き場 → 退避の順）         // 手順4
```

**実装順序が非対称になる点に注意する。** `moved`（上段→下段）は `arrangeBottomSlots()` を呼ぶ
**前**に決まるが、下段のこぼれは呼んだ**後**にしか分からない。§3-3 の排他性は件数の上で
成立しているので結果は変わらないが、コード上は一方向ずつ別の場所で処理することになる。
テストで「下段があふれた日は `moved` が空であること」を固定して、この前提を守る。

### 4-3. 印（フラグ）

`fromTop` は現状どおり残す（`renderSheet()` が引き出し線の id を落とすのに使っている）。
下段→上段の回送には引き出し線の問題が無い（上段に線は引かれない）ので新しい印は要らず、
注釈を作り直すだけで足りる。

### 4-4. 画面の通知（2026-09-19 に追加）

上段→下段の救済には画面通知がある（`fitSheetText()` 内、`files/index.html:4682`。`#sheetMsg` は
印刷CSSで `display:none` なので紙には出ない）。**下段→上段の回送にも同じ形の通知を出す。**
紙の上では PC横・EV横 が「軒下」の見出しの下に注釈つきで現れるので、画面側で理由を言わないと
現場が不具合と疑う。件数は欄の数ではなく荷物の数で数える（まとめた欄は複数のロットを含む）。

初版は §4-4「触らないもの」に `fitSheetText` を入れていたが、それでは回送が無言になる。
**`fitSheetText` は触る**。

### 4-5. 触らないもの

`sheetLayout` / `sheetEntries` / `slotAreaNote` / `mergeEntries` / `stashSlots` /
`arrangeOverflowSlots` / `overflowTable` / `drawLeaders` / `gridRows` /
`PRINT_ZOOM` / `SHEET_LAYOUTS`。

`SHEET_LAYOUTS` を触らない＝**今回は列を増やさない**。列増しは別の設計に切り出す（§7）。

## 5. テスト方針

サンドボックス実行方式（`new Function` で関数を組み立てて実際の戻り値を見る）で書く。ソース照合だけにしない。

**追加するテスト**

- 下段9欄・メイン9件・PC横1・EV横2 → 下段は全部メイン、PC横/EV横 は下段からこぼれる
- 下段9欄・メイン6件・PC横1・EV横1 → `メイン6 | 空1 | PC横 | EV横`（右詰めとEV横最右の維持）
- **残り1欄のとき PC横 が残る**（§3-2）。下段9欄・メイン8件・PC横1・EV横1 → 最右は PC横、EV横 がこぼれる
- **メインのこぼれは上段へ回さない**（§3-3）。下段があふれ上段に空きがある日でも、
  メインのこぼれは追記欄へ直行する
- 下段のこぼれのうち PC横・EV横 は上段の空き欄へ、注釈つきで入る
- 上段があふれ下段に空きがある日 → 既存の救済が変わらない（回帰）
- **下段があふれた日は `moved` が空**（§4-2 の排他性を固定する）
- 退避は実在する置き場の後、かつ上段の空きを先に使う（＝下段のこぼれより先に上段の欄を取る）
- 両段満杯 → 追記欄。順序は実在する置き場 → 退避
- **2026-09-19 のダミー実測の再現**（§2）: 下段候補が メイン系7欄・PC横3・EV横1 の日に、
  下段9欄が「メイン7＋PC横2」になり、こぼれが PC横1・EV横1 になること。
  改修前は メイン5＋PC横3＋EV横1 で、メイン2件が追記欄へ落ちていた

**書き替えが要りそうな既存テスト**（`tests/sheet-placement.test.js`、行番号は 2026-09-19 時点）

- `PC横・EV横ではEV横を右端に配置する`
- `PC横とEV横はメイン項目に挟まず右端へ連続配置する`
- `右端を予約してもメインロットは物理的に最短の下段欄へ置く`
- `sheetPlacementはグリッドセル中心に近い下段欄へメインロットを置く`
- `右端予約で欄数が減ってもあふれたメイン項目は入力順を保つ`

実装時に実際に落ちたものだけを、新しい期待値に書き替える。

## 6. 技術制約

`~/claude-lessons/lessons.md` を読んだうえで、この設計に効くものだけを挙げる。

- **テストの実行は `node --test tests/sheet-placement.test.js tests/stash-overflow.test.js`。**
  `node --test tests/` は Node v22.15.0 ではディレクトリを解決できず失敗する
- `sheetGridAnchors()` はデータ由来で DOM 実測を含まない（2026-09-17 実測確認）。
  ただし**紙の高さや欄幅を測る検証は配置図タブを表示してから**行う。
  非表示タブでは `getBoundingClientRect()` が 0（2026-08-23／2026-08-30 で2回踏んでいる）
- **計画に埋め込む検証スクリプトは、計画を確定する前に改修前のコードへ1回流す**（2026-08-30）
- `@media print` の中の宣言は `getComputedStyle` で読めない。CSSOM を走査する（2026-08-30）
- 開発中の再読込に `CACHE_VERSION` の繰り上げは効かない。ブラウザ検証の冒頭に
  **SW の unregister + `caches.delete()` + キャッシュバスティング付き URL** を定型で置く（2026-08-31）
- LAN 経由の実機は secure context でないため **SW が登録されない**。
  `CACHE_VERSION` の効果は実機では検証できない（2026-09-16）

### 6-1. 検証データを作るときの罠（2026-09-19 に3回踏んだ）

ブラウザで荷物を投入して検証する場合、次の3点を守らないと**数字が毎回変わる**。

1. **`clearLots()` は先頭で `confirm()` を出す。** 自動実行では否定されて何も消えない。
   `window.confirm` を一時的に差し替えてから呼ぶこと
2. **`clearLots()` は伝票ごと消すので入力欄が0行になる。** 先に `addSlip('fax')` で伝票を1枚作ってから
   `addItemRow()` で行を足す
3. **消さずに足すとロットが累積する。** `initLots()` が localStorage の保存分を読むため、
   リロードのたびに 16→31→42件と増える

動く投入コードの例（ロット16件・合計216P・退避47P の日を作る）:

```js
(()=>{const f=e=>e.dispatchEvent(new Event('input',{bubbles:true})),
```
