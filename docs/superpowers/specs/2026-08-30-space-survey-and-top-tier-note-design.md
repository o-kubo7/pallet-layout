## 1. 目的

現場で使えるパレット配置スペースを洗い出した結果を `DEFAULT_SPACES` に反映する。
あわせて、前案件の実機確認で見つかった「上段に移したエリアの注釈が出ない」を塞ぐ。

この 2 つを 1 件にまとめる理由は、どちらも配置図の表（以下「配置表」）に影響するため。
紙の様式を一度だけ見直せば済む。

## 3. 決定事項

ブレインストーミングで確定した方針を先にまとめる。

1. **軒下①の列分割は配置順に従う** — `[8, 11, 2, 3, 11]`。どの列も柱をまたがない
2. **ブロック図は実形に寄せる。柱は明示せず空白として現れる** — 列に描画位置を持たせる
3. **新規 2 エリアは自動配置の最後（あふれ受け）** — 出庫口横 → 5棟壁際 の順
4. **新規 2 エリアの掲載先は `top`** — 上段を「倉庫外の 4 エリア」にする。`zone` と段が一致する
5. **上段の注釈は下段と同じ流儀** — 上段の先頭（軒下①）を基準にして注釈なし、残りに `※` を付ける
6. **紙の様式は注釈行 1 行の追加のみ** — 欄数（上 4 / 下 7）と見出し「軒下」は据え置き。
   欄が足りないときの「上下段に 1 列追加」は次回にまわす
7. **倉庫外ブロック図は 3 列 × 2 行** — 実測の位置関係どおり
8. **描画位置は設定テキストに出さない** — コードの既定値だけが持つ

以下は `/dig` の実測指摘を受けて追加で決めたもの。

9. **印刷の `zoom` を 1.5 → 1.4 に下げる** — 注釈行 1 行で 1 ページに収まらなくなるため（§6-3）
10. **描画は CSS grid で組む** — flex とマージンでは同じ `off` の列が 13px ずれる（§7）
11. **物理的に離れた列が隣接扱いになるのは許容する** — 現行の軒下①も同じ前提だった（§5-2）
12. **バージョン不一致には専用の案内文を出す** — 「読み込めなかった」は誤解を招く（§8-6）

## 4. データモデルの追加

`col` に描画位置の任意属性を 2 つ足す。**配置ロジックには一切関与しない（描画専用）**。

- `row` … 描画上の行番号（0 始まり）
- `off` … その行内の開始オフセット（マス数、0 始まり）

省略時は従来どおり（`cols` の並び順に詰める / `off = 0`）。
エリア内に 1 つでも `row` を持つ列があれば、そのエリアを grid 描画に切り替える。

`flip:true` のエリアでは `off` は右端起点として扱う。`flip` は既存の
「短い段を右寄せする」CSS をそのまま使い、座標系だけ反転させる。

上限 `SPACES_MAX_ROW` / `SPACES_MAX_OFF` を追加する。
既存の `SPACES_MAX_COL_H = 99` と同じ理由（grid セルを作るので歯止めが要る）。

## 5. 新しい `DEFAULT_SPACES`

配列の並び順が自動配置の優先順であることは従来どおり。

```js
// メイン 74 — 変更なし。P列・T列の使用不可エリアは block:3 の隙間が担う
{name:"メイン", zone:"near", orient:"v", block:3, align:"top", sheet:"bottom", cols:[
   {h:6,aisle:true},{h:7},{h:7},{h:7},{h:7},{h:7},{h:7},{h:7},{h:7},{h:7},{h:5,aisle:true}]},

// 軒下① 30 → 35。列は配置順、row/off で実形にする
{name:"軒下①", zone:"far", orient:"h", block:99, sheet:"top", cols:[
   {h:8,  row:4, off:0},   // 1-8
   {h:11, row:3, off:0},   // 9-19
   {h:2,  row:4, off:9},   // 20-21（1-8 との間に柱 1 マス）
   {h:3,  row:0, off:9},   // 22-24
   {h:11, row:2, off:0}]}, // 25-35   ※ row1 は通路の空き行

// 軒下② 8 — 容量は同じだが向きが逆だった。v → h に直す（実測は横 4 × 縦 2）
{name:"軒下②", zone:"far", orient:"h", block:99, sheet:"top", cols:[{h:4},{h:4}]},

// PC横 12 — 列の順を配置順に入れ替え、通路の空き行を row で表す。flip:true は維持
{name:"PC横", zone:"near", orient:"h", block:99, sheet:"bottom", cols:[
   {h:4, row:0},           // 1-4
   {h:8, row:2}]},         // 5-12   ※ row1 は通路の空き行

// EV横 10 — L 字なので列を分割。flip:true は削除（実測は 1 が左端で、flip は誤りだった）
{name:"EV横", zone:"near", orient:"h", block:99, sheet:"bottom", cols:[
   {h:5, row:2, off:0},    // 1-5
   {h:1, row:3, off:4},    // 6
   {h:2, row:1, off:6},    // 7-8
   {h:2, row:0, off:6}]},  // 9-10

// 新規（あふれ受け）
{name:"出庫口横", zone:"far", orient:"h", block:99, sheet:"top", cols:[{h:2},{h:2}]},
{name:"5棟壁際", zone:"far", orient:"h", block:99, sheet:"top", cols:[{h:6},{h:6},{h:6}]},
```

付随する定数の変更:

- `AREA_GROUPS` は `[["軒下①","軒下②"]]` のまま。新規 2 エリアは連結しない
- `SPACES_SAVE_VERSION` を **1 → 2** に上げる。古い保存が捨てられ、更新した既定値が既存の端末に届く
- `FLOOR_POS`

```js
const FLOOR_POS = {
  "5棟壁際":{c:3,r:1},
  "軒下②":{c:1,r:2}, "出庫口横":{c:2,r:2}, "軒下①":{c:3,r:2},
  "メイン":{c:2,r:1}, "PC横":{c:1,r:2,flip:true}, "EV横":{c:2,r:2},
};
```

倉庫外と倉庫内は別コンテナ（`#zone-far` / `#zone-near`）に描かれるので、
`c`/`r` が重複していても衝突しない。これは現行も同じ。

### 5-1 承認済みの副作用

実形に合わせて列を割ると、1 列に連続して置ける長さが短くなる。

- **EV横** … これまで 6P のロットが 1 列に丸ごと入った。今後は `1-5` と `6` に分かれ、
  最大 5P 連続になる。実際の 5 と 6 は直角の位置関係なので、実態に近づく方向の変更
- **軒下①** … `1-8` と `20-21` が柱で分断される。現行も `[11,11,8]` で繋がっていなかったので
  実質的な変化はない

### 5-2 承認済みの副作用（逆方向）

`findRun()`（`files/index.html:1313`）と `blockCountOf()`（同 1686）は、
**配列で連続する列を物理的に隣接しているとみなす**。`cols` を配置順に並べると、
物理的に離れた列どうしが隣接扱いになる。

- 軒下① … `findRun(cols, 5)` が `[2, 3]` を返す。5P のロットがマス 20-21 と 22-24 に
  「一続き」として入り、`blockCountOf()` は 1 か所と報告する。実際は row4/off9 と
  row0/off9 で、間に通路行と 11 マスの行が 2 本ある
- EV横 … `findRun(cols, 3)` が `[1, 2]` を返す。マス 6 と 7-8 にまたがる

**これは許容する。** 理由は 2 つ。

1. 現場が振った番号は連番で、20 の次に 21・22 と置いていくのは運用上の意図どおり
2. 現行の軒下① `[11,11,8]` も行をまたいで連続扱いだった。この前提はもともと緩い

「2 か所に分かれます」の確認が出ないこと、紙に `※` が出ないこと（同一エリアなので
元々出ない）を承知のうえでの決定。

## 6. 配置表の変更

### 6-1 上段の基準エリア

`renderSheet()` の

```js
const top = sheetEntries(topAreas, null);
```

を

```js
const top = sheetEntries(topAreas, topAreas[0] || null);
```

に変える。これで上段の先頭エリア（既定では軒下①）以外に `※軒下②`・`※5棟壁際`・
`※出庫口横` が付く。下段の規則と揃うので、設定で並べ替えたときの振る舞いも同じになる。

### 6-2 上段の注釈行

現行の表は 8 行。行 4（上段のパレット数）の下に上段の注釈行を 1 行足して 9 行にする。

表は 14 列で組んである。行 3 の左ブロックは `rowspan="2"` で行 4 までしか届かないので、
新しい行では左 5 列を自分で埋める必要がある。

```js
rows += `<tr class="note-row"><td class="none" colspan="5"></td>${E}`
      + `${slotCells(top, SHEET_TOP_SLOTS, "note")}</tr>`;
```

列数は 5 + 1 + 4×2 = 14 で他の行と揃う。

セルの見た目は `slotCells()` が `kind === "note"` のときに付ける `.snote`
（`files/index.html:250`）がそのまま効く。`note-row` は下段の行にも付いているが
CSS 定義を持たないクラスなので、揃えるためだけに同じ名前を付ける。

### 6-3 印刷倍率を下げる

注釈行は**空でも 26px** 増える（`td.snote` の height 24px に罫線と padding が付く）。
実測した高さは次のとおり。

| | 表の高さ | zoom 1.5 での印刷時 | A4 横（余白 8mm）＝733.2px に対して |
|---|---|---|---|
| 現行 | 468.1px | 702.1px | 95.8% |
| 注釈行あり（注釈が空でも） | 494.1px | 741.1px | **101.1%** |
| 注釈が 2 行に折り返した場合 | 502.6px | 753.9px | **102.8%** |

`.sheet` は `page-break-inside:avoid` なので、収まらないと 2 ページ目へ丸ごと落ちる。
劣化が緩やかにならない。

`files/index.html:294` の印刷 CSS の `zoom` を **1.5 → 1.4** に下げる。
1.4 なら注釈が 2 行に折り返しても 96% で収まる。
上のコメント（「1.5倍で 1012×703px…」）も新しい数字に直す。

`※軒下②・出庫口横・5棟壁際` は 96px の欄で 2 行に折り返す（実測 26 → 34.5px）。
切れずに読めるが、この行が最も高くなるケースなので 1.4 の余裕はそのぶん必要。

### 6-4 欄数超過の警告も基準エリアを揃える

`renderResult()`（`files/index.html:1480`）の

```js
const overTop=sheetEntries(topAreas,null).length-SHEET_TOP_SLOTS;
```

も `topAreas[0]` に揃える。`length` しか使わないので動作は変わらないが、
揃えておかないと `renderSheet()` と別の基準を持つことになり、あとで意味がずれる。

### 6-5 触らないもの

- 欄数 `SHEET_TOP_SLOTS = 4` / `SHEET_BOTTOM_SLOTS = 7`
- 見出し「軒下」
- 引き出し線の起点（下段のパレット数行 `tr.btmp` の下辺）と
  `gridRows()` の 11 列ハードコード

グリッドはメインを描くもので、メインは変更しないため影響しない。

引き出し線の本数は「下段のロットのうちメインにも乗っているもの」の数で、
その日のロット一覧に完全に依存する。回帰の基準として使うなら、
リテラルではなく**改修前に測った値と同じか**で見ること。

## 7. 描画の変更（`drawZone`）

`row` を持つ列が 1 つでもあるエリアを「位置指定モード」とする。
`orient:"v"` のエリアは現行のまま。今回 `row`/`off` を使うのは `orient:"h"` のエリアのみ。

**CSS grid で組む。** 1 マス幅のトラックを並べ、各列を `grid-column: off+1 / span h` で置く。

```css
.grid-h.pos{display:grid;grid-auto-rows:auto;gap:5px}
```

トラック幅は `calc(var(--cell) + 2px)`（マス幅＋マス間の 2px）、トラック本数は
そのエリアの最大幅（`max(off + h)`）。

**flex とマージンでは同じ `off` の列が揃わない。** 実測で、軒下①のマス 22-24
（`off:9`）は左端から 288px、マス 20-21（同じ `off:9`）は 301px と 13px ずれた。
`.hrow` の border と padding（計 10px）と `.hline` の `gap`（5px）が
先行する列の本数だけ累積するため。実測の Excel では 22 と 20 は同じ列にあり、
縦に揃うべきもので、`§10-3` で人が目視確認する当のポイントに当たる。
grid なら同じ `off` は必ず同じトラックから始まるので、原理的にずれない。

grid の代償は、列の実幅がトラック幅より約 8px 広いこと
（`h × cell + 2(h−1) + 10` に対しトラックは `h × (cell + 2)`）。
右へ 8px はみ出すが、空きマス 1 つぶんのトラック幅（cell 30px のとき 32px）より
小さいので、隣の列とはぶつからない。行の右端でだけ枠が少し出る。

- `row` ごとに列をまとめ、`grid-row: row + 1` に置く
- 列が 1 つも無い `row`（軒下①の row1、PC横の row1）には高さ 1 マス分の空 div を
  その行に置く。これが通路の隙間になる
- `flip:true` のエリアでは、列位置を JS で反転して `grid-column` に入れる
  （`W − off − h + 1` から `span h`。`W` はそのエリアの最大幅）。
  CSS 側の `row-reverse` やマージンの左右分岐は不要

### 7-1 CSS クラス名

空き行のクラスは `.hgap` にする。`.empty` は使わない。
`files/index.html:152` に既存のグローバル `.empty`（`padding:26px 10px` ほか）があり、
そのまま当たると空き行が 30px ではなく 52px になり、色とセンタリングまで拾う。

このコードベースは同じ罠を一度踏んでいて、`files/index.html:249` に
「注記行は…グローバルの `.note` と衝突させないため別名」という注意書きが残っている。

### 7-2 列のキャプション

各列のキャプション（`3/3`）は現行どおり `colwrap` の中で列の下に置く。
`colwrap` は block なので、行の高さがキャプションのぶん増えるだけで重ならない。

## 8. 保存・設定への波及

### 8-1 `row`/`off` が落ちる 2 か所

保存そのもの（`saveData(STORE_KEY.spaces, {v:…, spaces:SPACES})`）は `SPACES` を丸ごと
JSON 化するので `row`/`off` も入る。落ちるのは次の 2 か所で、どちらも
`cols` を作り直している。

1. `normalizeSpaces()`（`files/index.html:2193`）— 復元時の正規化

```js
cols: s.cols.map(c => ({h:c.h, aisle:!!c.aisle}))
```

ここで落ちると、リロードのたびに形が崩れる。

2. `buildWork()`（`files/index.html:1334`）— 自動配置用の作業コピー

```js
cols: s.cols.map(c => ({h:c.h, aisle:!!c.aisle, fills:[]}))
```

`drawZone()` が受け取る `lastSp` はこの `buildWork()` の結果なので、
ここで落ちると**そもそも一度も実形で描かれない**。

どちらにも `row`/`off` を通す。`undefined` のまま持ち回ってよい
（`JSON.stringify` で消えるだけで、既定値の意味は変わらない）。

### 8-2 復元時の検証

`validSpaces()` で `row`/`off` を検証する。数値であること、
`0 <= row <= SPACES_MAX_ROW`、`0 <= off <= SPACES_MAX_OFF` を確認する。
既存の `h`・列数・エリア数の検証と同じ流儀（範囲外なら設定全体を捨てる）。

省略されている（`undefined`）のは正常な状態なので、存在するときだけ検証する。

### 8-3 設定テキスト

書式は**変更しない**。

```
名前 | 区分(near/far) | 向き(v/h) | ブロック列数 | 各列の高さ(末尾*=通路) | 掲載先(top/bottom/over)
```

`applyConfig()` は、そのエリアの列数が変わらなければ既存の `row`/`off` を列インデックスで
引き継ぎ、変わったら捨てる（捨てた列は従来どおり詰めて描かれる）。
`resetConfig()` で `DEFAULT_SPACES` に戻れば形も戻る。

`spacesToText()` は `row`/`off` を出力しない。したがって手動配置の指紋
`spacesToText(false)` にも入らない。

### 8-4 手動配置の指紋

指紋は列の高さを見る。軒下①の高さが `11,11,8` から `8,11,2,3,11` に変わるため、
既存の手動調整は指紋不一致で自動的に捨てられる。エリアの形が変わった以上、
これは意図どおりの挙動。

### 8-5 収容能力の表示

`showCapacity()` は `SPACES` から集計しているので、161P に自動で追従する。

`showCapacity()` は zone ごとの合計を出す（倉庫内はメイン・PC横・EV横をまとめた値）。
検証で期待値を書くときに、メイン単独の 63P と取り違えないこと。

- 改修前: 倉庫内 通常 85P ＋ 通路 11P ／ 倉庫外 通常 38P ＝ 134P
- 改修後: 倉庫内 通常 85P ＋ 通路 11P ／ 倉庫外 通常 65P ＝ 161P

### 8-6 バージョン更新時の案内文

`SPACES_SAVE_VERSION` を 2 に上げると、既存の端末はすべて `initSpaces()`
（`files/index.html:2616` 付近）の破棄パスに入り、

> 保存されていた設定を読み込めなかったので、初期値に戻しました。

が出る。壊れていたのではなく既定値を意図的に更新しただけなので、この文言は誤解を招く。
**バージョン不一致のときだけ別の文言を出す。**

```js
if(d.v!==SPACES_SAVE_VERSION){
  saveData(STORE_KEY.spaces, null);
  clearManual();
  showCfgNote("配置マスを現場の実測に合わせて更新したので、スペース設定と手動調整を初期値に戻しました。");
  return;
}
if(!validSpaces(d.spaces)){
  saveData(STORE_KEY.spaces, null);
  showCfgNote("保存されていた設定を読み込めなかったので、初期値に戻しました。");
  return;
}
```

手動調整は `restoreManual()` が指紋不一致で何の通知もなく捨てる
（`files/index.html:1901` 付近）ので、バージョン不一致のときは
`clearManual()` を明示的に呼んだうえで案内文に含める。
