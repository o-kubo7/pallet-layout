# 大きな配置図が出せないことを表の中で知らせる 設計書

- 作成: 2026-08-31
- 対象: `files/index.html`、`files/sw.js`
- 由来: `.superpowers/sdd/progress.md` の積み残し I-3（Important）

---

## 1. 問題

配置図の表の大きなグリッドは `gridRows()`（`files/index.html:2811`）が描く。
この関数は下段の先頭エリア（`sheetAreas("bottom")[0]`）の列を、紙の様式である
14 列の並び（通路｜1-3｜段番号｜4-6｜段番号｜7-9｜通路｜段番号）に流し込む。

```js
const order=[{c:0,aisle:true},{c:1},{c:2},{c:3},{lab:true,l:3,r:4},{c:4},{c:5},{c:6},{lab:true,l:6,r:7},
             {c:7},{c:8},{c:9},{c:10,aisle:true},{lab:true}];
if(order.some(o=>!o.lab && !sp.cols[o.c])) return {html:"", anchors:[]};
```

`order` は `sp.cols[0]` から `sp.cols[10]` までの 11 本を要求する。揃わないと
`sp.cols[o.c]` が `undefined` になって描画全体が落ちるため、`{html:"", anchors:[]}` を
返して**黙って大グリッドを描かない**。`!sp`（下段の先頭が見つからない）のときも同じ。

上段・下段の欄は正常に描かれるので、**グリッドと引き出し線だけが無い紙**が刷れる。
警告は一切出ず、`#messages` は「✅ すべてのパレットを配置しました。」のまま。

## 2. 発生経路（ブラウザで実測）

11 列を持つのは `メイン` だけ。次の 2 経路が現実的に踏まれる。

### 2-1. 行を並べ替えたとき（掲載先を触らない経路）

設定タブのヒント（`files/index.html:527`）は
「**行の順番には意味があります。**上の行から順に自動配置で試します」と案内している。
配置の優先順位を変えるつもりで `PC横` の行を上へ動かすと、下段の先頭が `PC横`（2 列）になり
グリッドが落ちる。

同じヒントの後半に「大きなグリッドは下段の基準エリアを描きます」とあるが、
優先順位を変える目的で操作している人がこの 2 つを結びつけるのは難しい。
**掲載先を触っている意識がないまま紙が壊れる**点で、これが最も踏みやすい。

実測: 並べ替えのみで `下段先頭=PC横 / tr.grow=0 / leaders=0`、警告なし。

### 2-2. メインの列数を 11 本より減らしたとき

通路を 1 本潰すなどして列を 11 → 10 にすると、下段の先頭はメインのままだが
`sp.cols[10]` が `undefined` になりグリッドが落ちる。

実測: `下段先頭=メイン / tr.grow=0`、警告なし。

現場の洗い出しを配置マス設定に反映した直後であり、今後レイアウトが変われば
再び列数を触ることになるため、将来また踏む経路である。

### 2-3. 起きないと確認した経路

- **改名**: グリッドは消えない。`gridRows()` は固定名ではなく「下段の先頭エリア」を
  見るので、改名しても先頭であり続ければ描ける（実測 `tr.grow=7`）。
  progress.md の「メインの改名でしか起きなかった」は `SHEET_BOTTOM` が
  ハードコード配列だった頃の記述で、現在は当てはまらない。
- **メインを `over` / `top` にする**: 機構としては起きるが、
  「現場でメインエリアを使用しないことはない」とユーザーが明言したため、
  実運用では発生しないものとして扱う。ただし機構上は 2-1 と同じ分岐に落ちるので、
  本設計の案内はこの経路もそのままカバーする。

## 3. あわせて直す件（12 列以上の無言の欠落）

同じ 11 列ハードコードに由来する別症状。メインの列を 12 本以上に増やすと
グリッド自体は描けるが、`order` が `sp.cols[11]` 以降を参照しないため
**12 列目以降のパレットが黙って紙から消える**（実測: `tr.grow=7` でグリッドは出る）。

検知も案内も I-3 と同じ場所に書けるため、今回の範囲に含める。

ただし**列があるだけでは知らせない。12 列目以降に実際にパレットが置かれている日だけ**出す。
`SPACES_MAX_COLS` は 40（`files/index.html:700`）なので、現場のレイアウトが育って
メインが恒久的に 12 列になった場合、無条件に出すと毎日刷る全ての紙に但し書きが載り続ける。
そのとき利用者に取れる対処は「倉庫の実態と違う設定を書く」しかない。実害がある日だけ鳴らす。

なお 12 列以上のとき、`order` は 11 列目（`{c:10,aisle:true}`）を通路として灰色に塗るので、
実際の通路が 12 列目にあれば**塗り分けの位置も実態とずれる**。パレットが消えるのとは別の症状だが、
同時に起きるので案内の文言で触れる（§7-3）。

## 4. 方針

グリッドが描けないこと自体は受け入れ、**表の中に案内を出す**。あわせて**設定タブでも知らせる**。

`#sheetMsg` は印刷 CSS（`files/index.html:330`）で `display:none` になるため、
紙には出ない。「グリッドの無い紙が黙って刷られる」ことを止めるには、
案内が**表そのものの中**にある必要がある。

ただし表の中の案内だけでは、気づくのが配置表タブを開いたときになる。
**事故を起こす瞬間は設定タブの中**であり、`renderSheet()` は配置表タブが表示されている
ときしか走らない（`files/index.html:1850`）。設定を反映した直後には表は組み直されない。

このプロジェクトには既に `showCfgNote()`（`files/index.html:2377`）があり、
`cfgNote` に文を出すと同時に `subtab-spaces` に `alert` クラスを付ける。
コメントに「配置マスのペインは閉じていることがあるので、サブタブに印を出して気づかせる」と
目的まで書かれている。同じ仕掛けに乗せて、`applyConfig()` の成功直後にも知らせる。

- **表の中の案内** — 印刷で消えないための本命。紙が壊れたまま刷られるのを止める
- **設定タブの知らせ** — 印刷する前に、操作したその場で気づかせる

## 5. 技術制約

`~/claude-lessons/lessons.md` から、この設計に効くものを引く。

- **印刷 CSS は `.note` と `.hint` を `!important` で消す**（`files/index.html:330`）。
  案内行にこの 2 つのクラス名を使ってはいけない。
- **背景色は既定で印刷されない**（2026-08-23 の教訓）。案内を背景色で目立たせる案は
  紙で消える。罫線と文字だけで表現する。`print-color-adjust:exact` を足す選択肢もあるが、
  プリンタドライバ側が優先しうるので採らない。
- **`@media print` の中の宣言は `getComputedStyle()` で読めない**（2026-08-30 の教訓）。
  印刷時の見え方を検証するときは `document.styleSheets` を走査し、
  `CSSRule.MEDIA_RULE` かつ `conditionText` に `print` を含むルールを探す。
- **非表示タブでは `getBoundingClientRect()` が 0 を返す**（2026-08-23 の教訓）。
  高さを測る検証の前に `switchTab('sheet')` を呼ぶ。
- **PWA は cache-first**（2026-07-09 の教訓）。`files/index.html` を変更したら
  `files/sw.js` の `CACHE_VERSION` を `"v23"` から `"v24"` に上げる。
- **`const order=` はファイル内に 2 か所ある。** `gridRows()` の 14 列の並び
  （`files/index.html:2818` 付近）のほかに、ロットの並べ替え（`files/index.html:1566`）にも
  同名の定数がある。実行計画で文字列置換を書くときは、一意に決まる行全体で指定する
  （2026-08-30 の教訓「replace の曖昧一致」）。

### 高さの予算

印刷は `.sheet{zoom:1.4}`。A4 横・余白 8mm の印刷領域は 733.2px、
現在の表は 1.4 倍で用紙の約 90.7% を使う。残りは約 68px（実寸換算 約 49px）。

**案内行の高さはブラウザに注入して実測した**（`font-size:10px` / `line-height:1.3` /
`padding:4px 2px`）。`.sheet td` の既定 `height:26px`（`files/index.html:247`）が下限になる。

| 文言 | 文字数 | 行数 | 高さ |
|---|---|---|---|
| `short` | 99 | 2 | 34px |
| `none` | 85 | 2 | 34px |
| `extra` | 56 | 1 | 26px |

- 経路 2-1 / 2-2 ではグリッド 8 行が丸ごと無いので、表はむしろ大幅に短い。余裕は十分。
- 12 列以上のケースはグリッドが出るが、`extra` は 1 行なので +26px 実寸。
  実測 472px + 26px = 498px、印刷時 697px。上限 718.5px に対し
  **印刷換算で 21px（実寸 15px）の余裕**がある。用紙比 95.1%。
- 表示設定で文字を大きくしている場合は既存の `fitSheetText()` の警告
  （「文字が大きくて印刷が1ページに収まりません」）がそのまま働く。新たな仕掛けは要らない。
  ただしその警告は真因を「文字が大きい」と名指しするので、案内行が加わって
  上限を跨いだ場合に原因を取り違えさせうる。既知の限界として受け入れる
  （`extra` は 1 行で、しかも荷物がある日だけ出るので、跨ぐ余地は小さい）。

### 幅の制約

表は 672px 固定。10px の全角なら 1 行あたり約 67 文字。
`short` と `none` は 80 文字を超えるので**2 行に折り返す**。
`white-space:normal` と `line-height:1.3` で組む。

エリア名の長さには上限が無い（`SPACES_MAX_AREAS=20` は個数の上限で、名前の長さは見ていない）。
20 文字のエリア名で `extra` を実測しても 1 行のままだったが、
35 文字を超えると折り返して高さが増える。上の余裕 21px を食い潰すほどではない。

## 6. 設計

### 6-1. 判定を `gridWarn()` に独立させる

`gridRows()` の中に判定を閉じ込めると、設定タブから使えない
（`renderSheet()` は配置表タブが開いているときしか走らない）。判定だけを取り出す。

まず、紙の様式である 14 列の並びを `gridRows()` の外に出して定数にする。
**様式が要求する列数はマジックナンバーにしない。** 並びから導く。

```js
const SHEET_GRID_ORDER=[{c:0,aisle:true},{c:1},{c:2},{c:3},{lab:true,l:3,r:4},
                        {c:4},{c:5},{c:6},{lab:true,l:6,r:7},
                        {c:7},{c:8},{c:9},{c:10,aisle:true},{lab:true}];
const SHEET_GRID_COLS=SHEET_GRID_ORDER.filter(o=>!o.lab).length;   // = 11
```

並びを将来変えれば、判定も案内の文言も自動で追随する。

```js
function gridWarn(sp){
  if(!sp) return {kind:"none"};
  if(sp.cols.length<SHEET_GRID_COLS)
    return {kind:"short", area:sp.name, cols:sp.cols.length, need:SHEET_GRID_COLS};
  // 列があるだけでは紙は狂わない。様式が参照しない列に荷物がある日だけ知らせる
  if(sp.cols.slice(SHEET_GRID_COLS).some(c=>c.fills && c.fills.length))
    return {kind:"extra", area:sp.name, cols:sp.cols.length, need:SHEET_GRID_COLS};
  return null;
}
```

`sp.cols.length<SHEET_GRID_COLS` は、現在の
`order.some(o=>!o.lab && !sp.cols[o.c])` と等価である。`buildWork()` が作る `cols` は
`SPACES.map(...).cols.map(...)` の密配列（`files/index.html:1470`）で穴が開かないため、
「必要な添字のどれかが `undefined`」と「本数が足りない」は同じ条件になる。

`gridRows()` は先頭で `gridWarn()` を呼び、戻り値を `{html, anchors, warn}` に広げる。
`"none"` と `"short"` のときは従来どおり `html:""` で返し、`"extra"` と `null` のときは
グリッドを組んで返す。**`kind:"extra"` のときも `html` は空でないので、
判定を `html` の空判定に寄せてはいけない。**

### 6-2. `renderSheet()` が案内行を組む

`gridRows()` の呼び出し直後に、`warn` から `<tr>` を 1 本作って差し込む。

```js
const grid=gridRows();
if(grid.warn && grid.warn.kind!=="extra") rows+=gridNoticeRow(grid.warn);
rows+=grid.html;
if(grid.warn && grid.warn.kind==="extra")  rows+=gridNoticeRow(grid.warn);
```

- `"none"` / `"short"` は**グリッドがあった位置**（下段の下）に置く。
  紙を見た人が「ここに図があるはずだ」と分かる位置に案内が出る。
- `"extra"` はグリッドが描けているので、**グリッドの下**に置く。
  正確にはグリッドの列番号行（`<tr>${nums}</tr>`）のさらに下になる。

文言は `gridNoticeText(warn)` が**素のテキスト**で返し、
`gridNoticeRow(warn)` がそれを `esc()` して `<tr>` に包む。2 つに分けるのは、
設定タブの `showCfgNote()` が `textContent` に入れるため、
エスケープ済みの文字列を渡すと実体参照がそのまま見えてしまうから。

### 6-3. 設定タブでも知らせる

`applyConfig()` の末尾、再配置（`redraw()` / `run(false)`）の後、
「設定を反映しました。」の `alert()` の前に置く。

```js
  // 配置表タブは開いていないことが多く、renderSheet() は開いているときしか走らない。
  // 紙が壊れる設定をした瞬間に気づけるよう、ここでも見る。
  if(hasResult && lastSp){
    const w=gridWarn(lastSp.find(s=>s.name===sheetAreas("bottom")[0]));
    if(w) showCfgNote(gridNoticeText(w));
  }
```

- `clearCfgNote()` より**後**に置く。先に置くと同じ関数の中で消される
- 再配置の**後**に置く。`lastSp` が新しい設定を反映していないと判定が古くなる
- `hasResult` で守る。結果が無ければ紙も無いので、知らせる意味がない
- `resetConfig()` には足さない。既定値は常に様式と合うので鳴らない

### 6-4. マークアップと CSS

```html
<tr class="gnote"><td colspan="14">※ ……</td></tr>
```

クラス名は `gnote`。既存の `note-row` / `snote` とも、印刷で消される
グローバルの `.note` / `.hint` とも衝突しない。

```css
.sheet tr.gnote td{border:0;background:transparent;
                   text-align:left;white-space:normal;
                   font-size:10px;line-height:1.3;color:#000;padding:4px 2px}
```

- `border:0` — 帳票の罫線を増やさない。案内は枠の外の但し書きとして読ませる
- `color:#000` — `snote` の `#333` ではなく黒。紙で薄くならないようにする
- 背景色は使わない（5 章の制約）

## 7. 文言

### 7-1. `kind:"short"`

> ※ メインエリアの配置図はこの表に出ていません。下段の先頭「PC横」は 2 列で、表の様式（11 列）に足りません。設定タブの「配置マス」で、ちょうど 11 列のエリアを下段の先頭行にしてください。

エリア名と実際の列数を埋めるので、「メインを上に動かした」場合も
「メインの列を減らした」場合も、同じ 1 文で原因が分かる。

**「11 列以上」ではなく「ちょうど 11 列」と書く。** 「以上」だと 12 列でも条件を満たすが、
そのとおりにすると今度は `kind:"extra"` に着地する。指示どおりにやって別の警告が出るのは、
直し方の案内として破綻している。

### 7-2. `kind:"none"`

> ※ メインエリアの配置図はこの表に出ていません。掲載先が「下段」のエリアがありません。設定タブの「配置マス」で、いずれかのエリアの掲載先を bottom にしてください。

### 7-3. `kind:"extra"`

> ※「メイン」の 12 列目以降はこの表に出ていません。表の様式は 11 列で、通路の位置も様式どおりに塗ります。

`「メイン」` の部分は先頭エリア名を実際の値から埋める。

後半の一文は §3 で述べた塗り分けのずれを指す。12 列以上のとき `order` は
11 列目を通路として塗るので、実際の通路が 12 列目にあると灰色の位置が実態と食い違う。
パレットが消えることだけを伝えると「灰色は正しい」と誤って安心させるため、あわせて書く。

実測でこの文言は 56 文字・**1 行**（26px）に収まる。

### 7-4. 「メインエリア」を固定で書くことについて

7-1 と 7-2 は「メインエリア」を文言に固定で持つ。ユーザーの指定による。
将来メインを改名した場合、実在しない名前を指す文になる。
現場でメインの呼び名が変わる見込みは薄いという判断で受け入れる。
7-3 は先頭エリア名を実際の値から埋めるので影響を受けない。

## 8. 今回の範囲外

- **下段の全欄に「※メイン」注釈が付く現象。** 基準エリアが `PC横` に変わると
  メインのロットが「よそ」扱いになるため付く。基準エリアの定義どおりの正しい挙動なので直さない。
- **グリッドの一般化**（11 列ハードコードの撤廃）。段番号列の位置・幅・引き出し線の終点など
  紙の様式そのものを作り直す大改修になる。今回は案内で留める。
- **設定側で反映を拒む案。** 経路 2-2（倉庫のレイアウトが実際に変わって列数を変える）まで
  拒むと設定を更新できなくなるため採らない。
- **通路の位置がずれている場合の是正。** `order` は先頭（`c:0`）と 11 本目（`c:10`）を
  通路として灰色に塗る。先頭エリアがちょうど 11 列でも通路がこの位置に無ければ、
  グリッドは描けるが塗り分けだけが実態と食い違う。**12 列以上のときは `extra` の文言で
  触れる**（§7-3）が、ちょうど 11 列で通路の位置だけが違う場合は検知しない。
  パレットが消えるわけではないので今回は扱わない。
- **`fitSheetText()` の警告の原因の名指し。** 案内行が加わって印刷の高さ上限を跨いだ場合、
  出るのは「文字が大きくて印刷が1ページに収まりません」であって真因を指さない。
  §5 のとおり余裕は 21px あり、`extra` は 1 行かつ荷物がある日だけ出るので、今回は直さない。
- **行方向の欠落。** グリッドは 7 行固定（`files/index.html:2917` の `for(let ri=0;ri<7;ri++)`、
  `circled` も 7 要素）だが、`SPACES_MAX_COL_H` は 99 まで許容している。下段の先頭エリアに
  高さ 8 以上の列があり、そこに 8 個目以降のパレットが載ると、そのマスは紙から黙って消える。
  `gridWarn()` は列数（`sp.cols.length`）としか比較していないため、この行方向の欠落には案内が
  出ない。今回は扱わないが、直すのであれば列方向と同じ設計（`SHEET_GRID_ROWS` を導出し、
  荷物が 8 行目以降に届いている日だけ `kind:"deep"` を出す）がそのまま使える。

## 9. 検証の方針

このプロジェクトにはテストランナーが無い。検証は `javascript_tool` で
検証スクリプトを実行し、返り値を確認する形で行う。

2026-08-30 の教訓に従い、**実行計画に埋め込む検証スクリプトは、計画を確定する前に
改修前のコードに対して一度走らせる**。参照する `getElementById` /
`querySelector` の引数は、単独で grep して実在を確かめる。本設計ではこれを実施済みで、
例外なく期待どおり空振りすることを確認してある。

### 検証スクリプトを書くときの落とし穴

- **`applyConfig()` は検証エラーで `alert()` して early return する。**
  検証スクリプトは `window.alert` を潰すので、**設定が適用されなかったことに気づけない**。
  前の状態のまま次を測り、紛らわしい合否が出る。設定を変える各手順の後に、
  `spacesToText()` か `sheetAreas("bottom")` が期待どおりかを必ず確かめる。
- **検証スクリプトを実機に貼らない。** 冒頭の `localStorage.clear()` は、
  実機で走らせると利用者の配置マス設定・品目マスタ・保存済み手動調整を消す。
  実機確認は画面を触る手順だけで行う。
